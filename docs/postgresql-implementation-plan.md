## 1. 목표와 범위

첫 목표는 FastAPI 서버를 재시작해도 문서와 편집 상태를 다시 조회하고 작업을 이어갈 수 있게 만드는 것이다. 이후 문서 버전·Job 기록·최소 인증을 추가해 동시 수정과 실패 상황에서도 기존 문서를 보존한다.

첫 구현 단위는 **DB 실행 환경 → 저장 설계 → 초안·세션 영속화**까지다. PostgreSQL 단계 전체 완료에는 버전 충돌·소유권·실패 복구 검증도 포함한다. 초기 영속화만 완료한 상태를 다중 사용자 서비스 완성으로 보지 않는다.

Redis/Worker, 자동 재시도, MCP, Kubernetes, 새 프런트엔드, LangGraph 노드 단위 체크포인트는 후속 범위다. 기존 UI와 폴링 흐름은 가능한 한 유지한다.

## 3. 설치 방법별 특징

아래 비교를 바탕으로 Docker Desktop + PostgreSQL 컨테이너 방식을 선택했다.

| 방식 | 장점 | 부담·주의점 | 적합한 상황 |
| --- | --- | --- | --- |
| Docker Desktop + PostgreSQL 컨테이너 | Compose로 실행 설정 공유, 프로젝트별 격리, 이후 Redis 추가가 쉬움 | WSL 2 등 실행 기반과 메모리·디스크 필요. Docker 실행 상태와 볼륨을 관리해야 함 | 이번 프로젝트의 추천안. 재현 가능한 로컬 환경과 후속 Worker 실습 |
| Windows 직접 설치 | Docker 없이 DB 서비스 사용. Windows 도구로 접근하기 쉬움 | 서비스·포트·계정·업그레이드를 PC별로 관리. 여러 프로젝트의 버전 분리 부담 | 컨테이너 도입보다 SQL·DB 연결을 먼저 익힐 때 |
| WSL 내부 Linux에 직접 설치 | Linux 서비스·권한·DB 관리 학습 가능 | Windows/WSL의 경로·네트워크·실행 환경을 구분해야 함 | 애플리케이션 개발도 WSL로 통일할 때 |
| 관리형 PostgreSQL | 로컬 DB 설치 부담 감소, 여러 환경에서 접속 가능 | 네트워크·TLS·접근 정책·비용 관리 필요. 백업·휴면·연결 제한은 공급자별 확인 | 배포 또는 공동 개발이 가까울 때 검토 |

### A. Docker Desktop + PostgreSQL — 추천안

1. Windows와 WSL 2 지원 조건, 가상화 활성화 및 사용 가능한 자원을 확인한다.
2. Docker Desktop 설치 후 엔진을 실행하고 `docker version`, `docker compose version`으로 확인한다.
3. 작성된 `compose.yaml`을 사용한다. PostgreSQL 이미지 버전, 개발 DB, 연결 포트, healthcheck, named volume을 명시한다.
4. 비밀번호는 커밋하지 않는 환경 파일에서 주입하고 예시 변수만 `.env.example`에 둔다.
5. 호스트의 FastAPI는 로컬 공개 포트로 연결한다. 향후 API도 컨테이너로 옮기면 호스트 주소 대신 Compose 서비스 이름을 사용한다.
6. 컨테이너 재생성 후 데이터 유지와 별도 백업 복원을 검증한다.

DB 포트는 로컬 개발용으로 루프백에 바인딩하고, 데이터는 OneDrive 저장소 내부 bind mount 대신 Docker named volume에 둔다. 컨테이너 삭제와 데이터 볼륨 삭제를 구분한다. 볼륨은 백업을 대체하지 않는다.

이미지 메이저 버전은 PostgreSQL 17로 고정했으며 `latest`는 사용하지 않는다. PostgreSQL 공식 이미지의 18 이상과 이전 버전은 기본 데이터 경로가 다르므로, 선택한 이미지 설명에 맞춰 볼륨 경로를 지정한다. 버전 숫자만 바꿔 기존 볼륨을 연결하는 방식으로 메이저 업그레이드하지 않는다.

설치 조건: [Docker Desktop Windows 설치](https://docs.docker.com/desktop/setup/install/windows-install/), [WSL 백엔드](https://docs.docker.com/desktop/features/wsl/). 이미지 설정 및 데이터 경로: [PostgreSQL 공식 Docker 이미지](https://hub.docker.com/_/postgres).

### B. Windows 직접 설치

1. PostgreSQL 공식 다운로드 페이지에서 안내하는 Windows 설치 프로그램을 사용한다.
2. 서버·명령행 도구를 설치하고 포트, 관리자 비밀번호, 데이터 디렉터리를 정한다.
3. 프로젝트 전용 DB와 애플리케이션 계정을 만든다. 앱에서 관리자 계정을 상시 사용하지 않는다.
4. Windows 서비스 실행 상태와 `psql` 접속을 확인한다. 명령을 찾지 못하면 설치 경로 또는 PATH를 점검한다.
5. `.env`의 DB 연결 문자열을 구성하고 서비스 재시작·백업·복원 절차를 기록한다.

데이터 디렉터리는 저장소 및 OneDrive 동기화 폴더 밖에 둔다. PostgreSQL 공식 페이지는 EDB가 제공하는 Windows 설치 프로그램을 안내한다. 세부 구성은 설치 시 선택한 버전을 기준으로 확인한다. [공식 Windows 설치 안내](https://www.postgresql.org/download/windows/)

### C. WSL 직접 설치 / 관리형 DB

WSL 방식은 배포판 설치 → PostgreSQL 패키지 설치 → 서비스·계정 구성 → 앱 접속 확인 순서로 진행한다. Windows에서 앱을 실행할지 WSL에서 함께 실행할지 먼저 정한다. 설치 명령과 서비스 관리는 배포판에 맞춰 확정한다. [Microsoft WSL 개발 환경 안내](https://learn.microsoft.com/en-us/windows/wsl/setup/environment)

관리형 DB는 공급자·리전·비용 범위를 정한 뒤 DB 생성 → 접근 정책·TLS 구성 → 연결 문자열 설정 → 마이그레이션·복원 확인 순서로 진행한다. 공급자는 현재 미정이며, 무료 제공 범위나 자동 백업을 가정하지 않는다.

## 4. 단계별 구현 계획

| 단계 | 상태 | 남은 완료 조건 |
| --- | --- | --- |
| 1. 실행 환경 | 완료 | Docker Desktop + PostgreSQL 17, 개발 DB·계정, 접속·재시작 데이터 유지 확인 |
| 2. 저장 설계 | 완료 | 1:1 문서·세션 관계, JSONB 상태, SQLAlchemy·psycopg·Alembic 선정 |
| 3. 문서·세션 영속화 | 완료 | DB 조회·저장·다운로드·목록·가져오기와 API 재시작 복원 검증 |
| 4. 버전·Job | 일부 완료 | 충돌 검사·실행 점유·중단 처리 완료. 과거 버전·Job·agent_runs·요청 중복 방지 필요 |
| 5. 인증·복구 | 일부 완료 | 별도 DB 백업 복원 수동 검증 완료. 로그인·사용자 격리·CI·운영 절차 필요 |

현재 `draft_revision`은 충돌 검사 번호이며 과거 본문을 보관하지 않는다.
`running` 중 요청을 거절하는 것과 같은 요청의 재전송을 멱등하게 처리하는 것은 별개다.
현재는 전자만 구현돼 있다.

단계 3까지는 로컬 단일 사용자 검증을 전제로 한다. 외부 사용자에게 공개하기 전에 단계 5를 완료한다. 각 단계는 독립된 커밋 또는 PR로 검토할 수 있도록 나눈다. 기간은 실행 환경과 인증 방식 확정 후 산정한다.

## 5. 데이터 모델 초안

아래는 전체 도입 목표 모델이다. 현재 적용된 DDL은 `001_storage` 마이그레이션이며,
`users`, `documents`, `sessions`만 구현돼 있다. 나머지 테이블은 후속 설계·구현 대상이다. `users`와 소유권 관계는 처음부터 모델에 반영하고 인증 연결은 별도 단계로 진행한다.

| 테이블 | 주요 데이터 | 핵심 규칙 |
| --- | --- | --- |
| `users` | 사용자 식별자, 인증 주체 연결 정보 | 인증 방식 확정 전 비밀번호 저장 방식을 임의로 도입하지 않음 |
| `sessions` | 소유자, 연결 문서, 대화·그래프 상태, 상태 스키마 버전 | 기존 세션 ID와 UI 흐름 유지, 상태 직렬화 왕복 검증 |
| `documents` | 소유자, 제목, 현재 버전, 생성·수정 시각 | 현재 버전 변경은 버전 저장과 같은 트랜잭션 |
| `document_versions` | 문서 ID, 버전, Markdown, Tiptap JSON, 생성 원인 | `(document_id, version)` 유일성, 기존 버전 불변 |
| `jobs` | 소유자, 문서·세션 ID, 기준 버전, 입력, 상태, 중복 키, 입력 해시 | 사용자별 중복 키 유일성, 같은 키·다른 입력은 충돌 |
| `agent_runs` | Job ID, 실행 시도, 시작·종료·오류 | 실행 시도와 결과를 추적할 수 있게 연결 |

`evaluations`는 이후 문서 버전과 평가 기준 버전에 연결한다. Redis 발행용 outbox와 lease/heartbeat 기반 실행 복구는 Worker 단계에서 도입한다.

SQLAlchemy 비동기·psycopg·Alembic 조합을 적용했다. FastAPI의 비동기 경로에서 DB 호출이 이벤트 루프를 막지 않도록 연결 방식을 정하고, 그래프의 동기 호출과 DB 트랜잭션 수명을 분리한다. LLM 호출 중 장시간 DB 트랜잭션을 유지하지 않는다.

## 6. 저장·API·실패 처리 계약

- 기존 `/api/sessions` API를 유지하고 목록·사본 생성 API를 추가했다. 문서 버전·Job 조회 API를 추가하고 최종 경로는 구현 전에 확정한다.
- 초안의 Markdown과 Tiptap JSON은 같은 트랜잭션에서 저장한다. 편집기 복원은 JSON, 미리보기·내보내기는 Markdown을 사용한다.
- LangChain 메시지는 단순 문자열로 축약하지 않고 역할·내용 등 필요한 정보를 왕복 복원한다. 그래프 상태 저장은 완료된 호출 경계에서 수행하며 노드 중간 재개와 구분한다.
- 파일 경로에만 의존하지 않도록 생성 결과 본문을 DB에 보존한다. 시각화 파일 등 부가 산출물의 저장·백업 경계는 별도로 기록한다.
- 현재 초안 저장은 `base_revision`을 포함한다. 후속 버전 이력 도입에서도 기존 필드와 호환성을 유지한다. DB에서 원자적으로 현재 버전을 비교한 뒤 새 버전과 현재 버전 포인터를 갱신한다. 충돌 시 409를 반환하고 최신 문서를 덮어쓰지 않는다.
- 생성 성공 시 문서 버전 저장과 Job 성공 처리를 한 트랜잭션으로 묶는다. 실패 시 기존 문서 버전은 유지한다.
- Job 저장 이후 실행을 시작한다. 동일 사용자·키·입력은 기존 Job을 반환하고, 같은 키·다른 입력은 거부한다.
- 이 단계의 실행은 단일 API 프로세스를 전제로 한다. 정상 종료 후 재기동 또는 비정상 종료 후 남은 작업은 중단/실패로 표시하고 자동 재실행하지 않는다. 사용자 재요청 시 새 실행 기록을 남긴다.
- 중단 상태 복구는 단일 인스턴스 운영 조건에서만 적용한다. 여러 인스턴스에서 실행 중인 작업을 일괄 실패 처리하지 않으며, 다중 Worker 지원은 lease와 실행 시도 검증을 도입한 뒤 진행한다.
- 모든 문서·Job 읽기/쓰기에서 인증 사용자와 소유자를 대조한다. UUID나 세션 ID를 아는 것만으로 접근 권한을 부여하지 않는다.

## 7. 기존 데이터와 운영 준비

기존 `output/drafts` 파일과 브라우저 초안은 삭제하지 않는다. 파일 가져오기는 소유자 지정, 원본 세션 ID 보존, JSON 검증, 재실행 시 중복 방지를 포함한 명시적 절차로 만든다. 파일에 없는 과거 대화나 실행 이력은 복원할 수 있다고 가정하지 않는다. 브라우저 초안은 사용자가 확인한 뒤 서버에 저장한다.

구현 시 개발 DB와 테스트 DB를 분리하고, 스키마 변경은 버전 관리되는 마이그레이션으로 적용한다. 기존 데이터가 있는 DB에서 초기화 명령을 실행하지 않는다. DB 연결 실패 시 메모리 저장으로 조용히 전환하지 않고 저장 실패를 사용자에게 알린다.

백업은 별도 파일로 생성하고 새 DB에 복원해 문서·버전·Job을 확인한다. 코드 롤백과 DB 스키마 롤백은 별도로 판단하며, 데이터 삭제가 필요한 역방향 마이그레이션 대신 백업 및 호환성 유지 방안을 먼저 검토한다.

## 8. 검증 계획

- 기존 Python 테스트와 Edge 편집기 테스트 유지. 변경된 요청 스키마에 맞춰 테스트 갱신.
- 실제 PostgreSQL에서 마이그레이션 적용과 세션·메시지·편집 JSON 저장/조회 검증.
- 별도 API 프로세스 재시작 후 같은 ID로 문서·대화·버전·Job 조회.
- 두 클라이언트의 같은 기준 버전 수정: 한 요청만 성공하고 다른 요청은 충돌.
- 같은 중복 키 재전송: Job·결과 버전 중복 없음. 입력이 달라지면 충돌.
- 모델 오류·DB 오류·실행 도중 프로세스 종료: 원문 유지, 작업 상태 식별, 완료 작업 재실행 없음.
- 서로 다른 사용자로 문서·Job·다운로드 접근 차단 확인.
- DB 백업을 새 DB에 복원한 뒤 저장 데이터와 조회 결과 비교.

DB·실패 테스트는 모의 모델로 먼저 검증하고 실제 모델은 작은 종단 사례로 확인한다. SQLite 대체 테스트만으로 PostgreSQL 동시성 검증을 완료했다고 판단하지 않는다.

## 10. 남은 구현 순서와 완료 판정

1. **문서 버전:** 기존 최신본의 초기 버전 이관, 변경 본문 보관, 이력 조회·복원.
   복원은 과거 버전 수정이 아니라 새 버전 생성으로 처리하고 현재 revision 충돌을 검사한다.
2. **Job·실행 이력:** 실행 전에 요청 저장, 중복 키·입력 해시 검증, 성공 결과와 상태 동시 커밋,
   중단·실패 기록과 명시적 재요청. 자동 재시도·Redis Worker는 이번 범위 밖이다.
3. **인증·소유권:** 선택한 인증 방식 적용, 모든 문서·세션·버전·Job·다운로드 경로의 소유자 확인,
   기존 개발 사용자 데이터의 명시적 인계와 다른 사용자 접근 차단 검증.
4. **운영·최종 검증:** 실제 PostgreSQL CI, 버전·Job까지 포함한 백업 복원,
   모의 모델 장애·재시작·중복·동시성 테스트, 실제 모델의 작은 종단 사례 확인.

1~3단계 완료를 PostgreSQL 도입 전체 완료로 표시하지 않는다. 위 후속 기능과 검증이
끝난 뒤 전체 완료로 전환한다. 외부 설치·이미지·모델 다운로드가 필요하면 사용자가
직접 실행하며, 준비되지 않은 환경의 검증은 미검증으로 기록한다.


## 11. 후속 구현 진행 상태
